AgentSense · WeRead Channel

自愈模块改造方案

这次断线的教训不是"续期没生效"，而是：自愈只有一根杠杆，而且没有验证。它把 -2012 换成了 -2041，还让故障从"每轮失败"变成"每轮都在叫你去扫码"。

01 · 现状

现在的"自愈"做了什么、漏了什么

能力当前实现问题
修复动作只调 POST /web/login/renewal 换 wr_skey 单杠杆：所有鉴权码都走这一条，包括根本不是会话问题的 -2041
修复判据succ == 1 就认为修好了 没有验证：实测续期确实 succ=1，但文章接口仍被拒 ⇒ "修好了"是假象
失败处理raise SystemExit("请扫码") 没有降级阶梯：一条接口挂掉 = 整轮 6 个号全灭
频率控制无会放大故障：每撞一次就再续一次，一轮能续十几次
可观测性只有一行中文输出事后分不清"修了没用"和"根本没修"

一句话概括：它修的是"会话过期"，但没定义"什么算修好"。于是当平台换了拒绝方式（-2041），它继续按老剧本演，把一个可降级的故障升级成了整轮失败。

02 · 原则

自愈的三条纪律

① 可验证

修复后必须跑一次独立哨兵请求，通过才算修好。返回码只说明"请求发出去了"，不说明"权限回来了"。

② 不放大

自愈本身要有预算、退避、熔断。一个会无限重试的自愈，是第二个故障源。

③ 留痕

每次尝试写一条结构化记录（码、动作、哨兵结果、耗时），否则永远在猜"上次到底修没修"。

03 · 架构

五层状态机：观测 → 归因 → 修复 → 验证 → 降级

L0 观测   记录 (path, errCode, 耗时, 响应大小)
   ↓
L1 归因   会话问题? ── 跑哨兵 /web/shelf/sync（books>0 且 synckey 存在）
   │         ├─ 哨兵失败 → 「会话死」   → 只能人工扫码
   │         └─ 哨兵通过 → 「会话活」
   ↓
L2 修复   仅「会话死」才续期；「会话活 + 目标接口拒绝」不做任何修复
   ↓
L3 验证   续期后再跑一次哨兵；通过 → 记为已修复；失败 → 升级为「会话死」
   ↓
L4 降级   主通道不可用 → cover → 合集通道 → 待采队列（记缺口，恢复后回填）
   ↓
   升级   同一原因连续 N 轮 → 熔断 T 小时 + 分级告警

决策表（这张表是整个模块的核心）

错误码 / 现象哨兵结果动作验证与退避
-2010 / -2012失败（0 本）续期 1 次续期后重跑哨兵；仍失败 ⇒ 判「会话死」
-2010 / -2012通过（>0 本）续期 1 次后重试原请求仍失败 ⇒ 按接口问题处理
-2041通过不续期、不重试，直接降级降级通道探活；30 分钟冷却
超时 / 5xx—指数退避重试 2 次（30s / 90s）不触碰会话
连续 3 轮同因—熔断 6h + 告警熔断期内不再尝试，避免打穿账号

为什么哨兵选 /web/shelf/sync：① 匿名访问返回 -2010 / 0 本，登录态返回 416 本 + synckey，判据极清晰；② 一次请求、开销小；③ 不碰内容接口，不消耗公众号额度。它就是这次能证明"会话是好的"的那个实验，应当固化成代码，而不是留在排查笔记里。

04 · 降级阶梯

一条通道挂了，不该等于整轮失败

层级通道能力与代价
T0/web/mp/articles全量列表（一页 20 个群发、可翻页）—— 首选
T1/web/mp/cover只返回最新 1 篇（实测 offset 无效）—— 保底，但必须标注"覆盖率下降"
T2合集通道 album_collector只覆盖"已登记合集"的号；对机构号通常不适用
T3待采队列（新增）把 {账号, 起始时间, 原因} 记下来；主通道恢复后按 originalId 幂等回填

T3 是这次缺的关键一环。T1 只能取 1 篇，而混沌天成一天发 5 篇早评 —— 降级跑成功后，缺口会静默消失：水位线照样更新，第二天再也补不回来。所以降级时必须记缺口，而不是"能取一篇就算过"。

05 · 可观测性

把"修没修好"变成一份可读的状态文件

~/.tradingagents/weread/health.json
{
  "checked_at": "2026-10-21T09:20:00",
  "session":     {"ok": true,  "probe_books": 416, "renewed_at": "09:13", "renew_count": 1},
  "endpoints":   {"articles": {"ok": false, "code": -2041, "since": "2026-10-19"},
                  "cover":    {"ok": true},
                  "album":    {"ok": true}},
  "degraded":    {"accounts": ["混沌天成研究", "紫金天风期货研究所"],
                  "reason": "articles_refused", "coverage": "latest_only"},
  "backlog":     [{"account": "混沌天成研究", "since": "2026-10-21T00:00:00", "reason": "articles_refused"}],
  "next_action": "无需扫码；等待 articles 恢复后按 backlog 回填"
}

有了它，告警就能说人话："会话正常，是文章接口被拒，已降级并记账"，而不是永远一句"请扫码"。

告警分级

级别触发文案要点
info单号降级、仍有产出"本轮 2 个号降级为最新 1 篇，缺口已记账"
warning全部号降级 / 连续 2 轮"文章接口持续被拒（会话正常），非登录问题，勿扫码"
critical哨兵失败（会话真死）"会话已失效，需扫码：node probe/_weread_login.mjs"
06 · 路线

四步走，每步都可独立验收

阶段内容验收（全部可测）
P0
已完成		 错误码分层（-2041 独立）+ 单号降级 + 续期预算 + dry-run 隔离 11 例护栏 + 变异 7/7；真机 dry-run：不退出、报降级、exit 0
P1 哨兵探针 + 决策表 + health.json 注入 -2012/-2041 两种码，断言"是否续期""是否降级""health 字段正确"
P2 待采队列 + 恢复后自动回填（按 originalId 幂等） 降级期间漏 5 篇 → 主通道恢复后 5 篇全部补回，且不重复
P3 熔断与告警分级（连续 3 轮同因 → 冷却 6h） 模拟 3 轮失败，断言第 4 轮不再发请求、告警级别为 warning
07 · 边界

这套改造解决什么、不解决什么

能解决

故障不再被误判成"登录过期"；一条接口挂掉不会拖垮整轮；续期不会越修越糟；缺口可追溯、可回填；告警说人话。

不能解决

平台为什么拒 -2041。那是服务端策略，本地无法绕过。如果它长期不恢复，只能换通道（浏览器/其它来源），而不是继续加自愈。

这次的时间线值得记住：10-19 上续期后 -2012 消失、-2041 出现，中间只有 10-20 18:33 成功过一次 —— 自愈把一个稳定故障换成了不稳定故障，而监控没跟着变。所以 P1 的重点不是"更强的修复"，而是"更准的归因"。
