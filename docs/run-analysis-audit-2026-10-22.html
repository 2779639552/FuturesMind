四、另外三件顺手查到的事

1. 方法论块为什么排在最前？

因为它是最后一个 prepend 的。代码里所有注入都是 system_message = 块 + "\n\n" + system_message，谁在后面执行谁就排最前。执行顺序是「方法论 → 品种库 → 三轴 → 四源」，于是最终顺序整个倒过来：方法论第一、四源第四。

新块（P0/P1）的注释写着「确定性前置到系统提示最前面」，但它们只比框架说明书靠前，并不比 2026-09-29 加的方法论块靠前。计划文档里「全部放在 system prompt 最前」这句话，从来没有真正实现过。

2. 超时不写日志

_snapshot() 和 gtja_context() 的等待分支都是「ev.wait(8) → 查缓存 → 有就返回，没有就 return ""」，一行日志都没有。线上如果注入块长期缺席，日志里查不到任何痕迹 —— 这也是为什么它藏了三天没人发现。

3. 单飞缓存没有异常写回

analysis_bundle.gtja_context 的工作线程里，_CACHE[sym] = (time.time(), text) 在 try 里但没有 except：build_block 一旦抛异常，事件会 set、缓存却没写，之后每次调用都会重新起线程重试。属于低频路径，但会让「失败」变成「每次都重试」而不是「记住失败」。

七、日线磁盘缓存（15:05 落地）——顺带发现缓存层根本没接上

继续查「首次分析干等 16s」时，发现根因不是天勤慢，而是两层缓存都没生效。

第一层：只有 5 分钟内存缓存，跨进程就没了

quant_module._daily_bars_cached 的 TTL 是 _TTL_OVERVIEW（5 分钟）。服务一重启、或隔天再分析，内存必空 ⇒ 必付日线取数：天勤短连接 5.4s，失败回退 AKShare 8.7s。

第二层（更关键）：运行分析压根没走这个缓存

analyst_views._build_payload 里写的是 q._load_daily_bars(sym, 250) —— 直接实拉，绕过了 _daily_bars_cached。
cProfile 实证：一次 _compute 里 _load_daily_bars 被调用 2 次、累计 6.819s，而缓存层一次都没被调用。
也就是说：这个 5 分钟缓存从上线起就只服务「量化页的技术快照」，运行分析一次都没享受过。

改法（两处，互不耦合）

改动规则
① 新增磁盘层
_disk_read / _disk_write		 只在非交易时段读写（日盘 09:00–15:10、夜盘 21:00–23:30 一律不读不写）。
理由：日线最后一根在盘中持续更新，那时落盘拿到的是未完成 bar，收盘价不是最终值，喂给 MA/RSI 就是错的。
TTL 18h（15:10 落盘 → 次日 08:55 仍命中）；数据日期超 10 天、文件损坏、结构不符一律当作没有。
② _build_payload 改走
_daily_bars_cached		 接上缓存层。同时确认下游只读不写（pd.DataFrame(bars) 是拷贝），避免共享 list 被原地修改。
③ 全仓统一收口
（再发现 6 处绕过）		 顺着调用图往上追，发现同一份日线被拉了不止一次：
methodology_context.py ×3（技术/基本面方法论块、跨品种套利）、 fund_module.py ×2（四象输入、按合约月重算）、 signal_analyzer.py ×1（回测价格序列）。
